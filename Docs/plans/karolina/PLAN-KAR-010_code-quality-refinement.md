## 实施细节

1. 将说明进度从Workbench共享字段提取为独立Core服务。它唯一拥有按ReviewId/RunId绑定的不可变状态；存储通过专用接口注入，TimeProvider控制时钟。JSON存储独立负责路径核验、读取与原子落盘，既有字段/文件位置不变。
2. Codex app-server提供连接端口；Workbench可注入协议实现、证据存储和说明服务，生产入口仍默认组合现有实现。接口说明现有app-server协议，不宣称已实现其它Harness。
3. 将执行回复及冻结说明落库用例提取为ReviewCompletionService，保留原TaskReviewStore的来源/版本核验及部分回复错误语义。
4. HTTP合同、请求映射、执行流程、Unity调度分别组织；避免仅新增partial就宣称降低共享状态耦合。终态仍统一Finish，锁顺序与停止轮次核验不变。
5. 前端提取模型/档位纯政策及进度文本计算，工具函数卡片独立视图接收调用回调；控制器保留API/状态/错误处理，用户视觉和选择语义不变。
6. 构建信息从实际index.html单一版本标记读取，前后端不再各写一份版本字符串。更新架构事实，按七原则说明实得及剩余边界。

## 文件预估与数据流

Core增加协议端口、进度状态服务与JSON存储；Desktop调整Workbench依赖和进度接线，拆分HTTP合同/Routes/Chat/Unity；Web增加政策模块和工具操作视图。当期仅变更 Karolina 源码与文档；不迁移审批、改写 Unity 资源或清理已有实现。

Codex通知→Workbench核对当前thread/turn→说明服务按ReviewId/RunId更新→API读取快照→UI政策格式化。开始及终态→存储端口→原子JSON；存储失败在内存与事件中可见且不阻止执行锁释放。旧运行进度启动时恢复，Active无终态标为中断。存储不发布回调，避免状态锁与宿主聊天/事件锁互相调用。
