# 构建菜单与外部GUI工具调用

## 目标实现

工具页聚焦项目实际操作：构建客户端/服务端/本地与UOS、发布参数窗口，以及UOS客户端GUI和游戏GUI启动器。去掉Console、Editor状态和.NET环境独立工具。

## 技术方案

Unity菜单通过现有MCP执行固定菜单；构建请求只发一次，pending护栏暂停后续Unity调用直到用户确认。外部GUI使用独立启动模式，回执仅表示进程已启动，不等待退出、不杀用户GUI；缺失exe明确提示。

### 菜单与声明合同

工具注册保留 kind、guideId、readOnly 等共同字段；kind=group和operations组织一组相关调用函数，不嵌套集合。每个函数有独立英文id、标题、入口及参数，集合共用使用说明，Unity菜单增加固定 menuPath，外部程序增加 launchMode。菜单对照工程现有MenuItem白名单，不允许界面任意拼接执行脚本。通过MCP script-execute调用 EditorApplication.ExecuteMenuItem，菜单不存在须可见失败。

“项目构建”一个工具页面包含本地/UOS的客户端、服务端、双端构建及发布参数窗口共七个函数。目录仅列语义工具，函数在同页调用，不把每个函数拆成一个工具页面。人工调用无需选择计划/继续任务，不自动创建Agent审批；调用仍保存所属工具及函数、结果和错误，共享工程锁与构建纪律不变。组的声明哈希保护所有子函数，修改任一函数后拒绝旧声明调用。真正构建声明必须带unityBuild，调用前写入pending，发送一次后等待用户确认结束，不自动重试；请求失败但是否已开始不明也保留待确认。发布参数窗口仅打开配置，不假定点击窗口即完成构建。

UOS GUI入口为 Builds/Tools/UosClientLauncher/FrameSyncMoba.UosClientLauncher.exe，游戏GUI为 Builds/Demo/Launcher/FrameSyncMobaLauncher.exe；通过明确可执行路径和ArgumentList启动，不经shell拼接。GUI模式只回报PID，不等待用户关窗、不在工具超时或Karolina退出时杀启动器。普通命令等待模式维持既有输出和超时行为。

调用区支持整组和各函数单独折叠，函数标题、说明和按钮对齐。渲染函数后立即更新按钮，说明和历史读取不阻塞调用。Codex连接及账号/模型刷新采用独立连接锁，不能占用工具执行锁造成长时间排队；真实工程任务/工具仍互斥，页面说明阻塞原因。执行锁正在处理其它操作时直接返回可见提示，不在后台积压调用。

## 边界情况

并发修改与陈旧版本必须可见拒绝；不能把机器静态摘要视为行为验收。保留既有美术交互、已有Unity改动及审批存档。失败不补造成功。

没有连接Unity或没有exe时显示真实错误，不代替用户安装/构建。pending期间Unity连接重试、Unity工具与Harness新轮次均暂停，以避免独立MCP越过构建纪律。构建输出仍在忽略的Builds目录，只有用户接受发布才进入Release。工具说明也有最多10个标签，与规则案分开。

## 验收条件

通过对应计划的机器检查与独立Agent审查，用户操作确认后才能关闭。禁止截图验收。

## 需求演进

### 2026-10-04 · 首次建立

根据用户十项功能优化要求拆分建立；不迁移旧文档结论作为本轮成功证据。

### 2026-10-05 · 多函数工具与人工直接调用

用户要求删除工具页“执行计划/继续原任务”，一个工具支持多个相同语义函数。构建合并为七函数工具，游戏/UOS启动器分别保留独立语义页面，可继续注册更多相关函数。移除工具调用与Agent执行计划/审批的强耦合；人工调用记录不会伪造Agent修改来源。

### 2026-10-05 · 调用响应与折叠排列

用户反馈进入工具页后需要长时间等待才能调用，并要求排列整齐、可折叠。拆开Codex连接刷新与工具执行锁，保留实际执行互斥、Unity身份校验与构建pending纪律；整组及各函数均提供折叠入口。
